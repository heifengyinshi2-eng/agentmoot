参会成员守则（按角色区分）

已注入各角色 prompt，详见 docs/committee-code.md

发起方守则

【发起方守则】
1. 你是提案的设计者，方案必须说详细：涉及接口/协议/数据结构/状态机变更时，必须给出代码或伪代码（签名、字段、流转、输入输出、边界行为）。
2. 发言三要素：自然说清问题（现状哪里不对）、诉求（要解决什么）、解决方案（具体怎么改，含代码/伪代码）；缺一不合格，不要机械分三段列标题。
3. 简明但完整：不堆背景、不车轱辘话；但方案本身不能含糊，要能落到可执行。

非发起参与方守则

【参会成员守则】（针对非发起方：表态/提反对/提补充）
1. 以问题和诉求为主：说清问题（现状哪里不对）、诉求（我方需要/不能接受什么）；解决方案只需简要说明方向即可，不要替发起方写完整方案或代码。
2. 简明扼要：一句话能说清不用一段；禁止车轱辘话、重复已定内容、堆砌背景。
3. 就事论事：只对提案本身表态，只说自己项目的约束边界，不替别的项目做决定；领域否决要给出"不能接受的具体点"。
4. 表态边界：accept 无附加文本；reject 说清问题+诉求+不能接受的具体点；supplement 给出问题+诉求+简版方案方向。

主持守则（chair）

【主持守则】
只引导不给方案；判定时归纳分歧点、以提案编号+修订号指代；决议汇编列出分工、共识、未决项。简明扼要，就事论事。

[dep-app] 创建 issue I-001: JSON 序列化大整数（> 2^53）精度丢失
  正文: ## 问题
base-lib 的 JSON 序列化在遇到超过 2^53 的整数（雪花 ID、订单号、纳秒时间戳等）时会发生精度丢失，序列化结果被舍入，导致数据不可逆。

## 复现步骤
1. 安装 base-lib（当前最新版本）。
2. 执行：
```js
const lib = require('base-lib');
const v = 9007199254740993n; // 2^53 + 1
const s = lib.stringify({ id: v });
console.log(s);
console.log(JSON.parse(s).id);
```
3. 观察输出。

## 实际行为
输出 `{"id":9007199254740992}`，末尾 93 被舍入为 92，`parse(stringify(x))` 无法还原原值。

## 期望行为
大整数序列化后保持原始精度，例如 `{"id":"9007199254740993"}` 或其他可逆表示；即对任意大整数满足 `parse(stringify(x)) === x`。

## 影响
dep-app 的实体 ID 经 base-lib 序列化后与数据库、下游服务不一致，导致记录查不到或关联错误。请评估修复方案（如大整数转字符串输出）。

[base-lib] 评审 → accepted（大整数精度丢失是真实且常见的兼容性问题：JSON 中常出现雪花 ID、订单号、纳秒时间戳等超过 2^53 的整数，序列化时静默舍入会破坏数据可逆性与跨服务一致性。issue 的复现、实际行为（末位被舍入为偶数）、期望行为（无损表示）均清晰合理，且影响面（dep-app 实体 ID 与数据库/下游不一致）成立。应在序列化层提供无损方案，如支持 BigInt 并默认将超出 ±Number.MAX_SAFE_INTEGER 的整数序列化为字符串，同时提供配置项显式选择旧的 number 行为；默认输出格式变化需按语义化版本发布并在变更说明中提示依赖方调整反序列化。）

[base-lib] resolve → 根因：stringify 把 BigInt 和超出安全范围的整数先转成 Number 再序列化，导致 >2^53 的值被静默舍入；parse 也没有对应的恢复逻辑。修复：序列化层直接识别 bigint 及 |n|>Number.MAX_SAFE_INTEGER 的整数，统一输出为十进制字符串（如 id 变为 "9007199254740993"），不再经过 Number；无损模式默认开启，并保留 legacyNumberMode 配置显式回退旧的 number 行为（仅作过渡，仍存在精度风险）。同时给 parse 增加 BigInt reviver 选项：开启后这类字符串会还原为 BigInt，从而满足 parse(stringify(x)) === x；默认 parse 返回字符串，与线格式一致。对使用方的影响：ID 等字段在线路上的类型由 number 变为 string，dep-app 需按字符串比较和透传、DB 层按字符串绑定，不能直接做算术；默认线格式变化属于可观察行为变更，按 semver major 发布，并在 CHANGELOG 中说明迁移方式（未开启 reviver 时按字符串处理）。

处理提案 P1（发起方 base）：X 接口参数从 int 改为 string 以支持大整数

  —— 第 1 轮表态（并行盲投）——
    [mw] → supplement：补充: 版本 v1：X 接口新增字符串重载以支持大整数，同时保留既有 int 接口。

签名：
`void setX(int x); int getX();`（既有语义不变）
`void setXString(string x); string getXString();`（新增大整数通道）

语义：x 为十进制整数字符串，接收方按 BigInt 解析；格式固定为 `^-?(0|[1-9][0-9]*)$`（禁止前导零、+号、空白、空串），不合格式返回 E_FORMAT；数值超出有符号 64 位范围返回 E_RANGE。
    [app] → accept

    [chair] 判定 → continue：分歧点：P1 v1 主张将 int 参数改为 string，破坏兼容；mw 补充主张保留 int 并新增 string 重载（setXString），即兼容路线。两者互斥。请 mw 与 app 就“是否允许破坏性变更”表态，并请 base 据此出 P1 v2 单一方案（替换或重载二选一），再表态。
    [base] 提出新版本 v2：P1 v2 单一方案（二选一，采用「兼容新增」路线，放弃 int→string 破坏性替换）

一、现状问题
现有签名 void setX(int x); int getX(); 在超过 2^53 的场景经 JS/跨语言 JSON 传输会丢精度，int 字段本身也无法承载大整数；但直接把参数类型改成 string 会同时破坏既有调用方、已持久化数据和线上协议（当前协议无版本协商、无灰度字段），属于不可接受的破坏性变更。

二、诉求
1) 支持大整数（十进制字符串）写入与读回；2) 既有 setX(int)/getX() 的签名、语义、序列化字段、错误码完全不变；3) 新旧调用方可并存、按调用方灰度、可随时回滚。

三、方案：保留 int 接口，新增具名字符串接口（不做同名重载，避免隐式转换歧义）

接口签名（Java 示意，其他语言同构）：

    public interface XService {
        // 既有接口，语义与错误码完全不变
        void setX(int x);
        int getX();

        // 新增：字符串入口/出口
        void setXString(String x);   // 输入十进制整数字符串
        String getXString();         // 输出规范十进制字符串
    }

内部状态：单一不可变对象，BigInteger 为唯一真值，int 仅作范围内缓存：

    final class XState {
        final BigInteger value;  // 唯一真值
        final Integer asInt;     // 落在 int 范围时为缓存值，否则 null
    }
    private volatile XState state = new XState(BigInteger.ZERO, 0);

流转：
- setX(int x)：state = new XState(BigInteger.valueOf(x), x)；
- setXString(String s)：先校验格式，再规范化（去前导零、-0→0），最后 state = new XState(v, v.bitLength() < 32 ? v.intValue() : null)；
- getX()：state.asInt != null 时返回 asInt，否则抛 E_RANGE（明确：字符串写入超出 int 后再调旧 getX 报 E_RANGE，绝不截断/溢出）；
- getXString()：返回 state.value.toString()。

输入输出边界（setXString）：
- null、空串、"+"、"-" → E_FORMAT；
- 含空白、下划线、小数点、科学计数、0x 前缀 → E_FORMAT（不 trim、不猜测）；
- 不匹配 ^[+-]?[0-9]+$ → E_FORMAT；
- "0"/"-0"/"+0"/"000" → 接受，规范化为 "0"；
- "00123" → 接受，规范化为 "123"；
- 去符号与前导零后的位数 > MAX_DIGITS(4096，可配) → E_RANGE（防 DoS）；
- 合法且在位数上限内 → 成功存储 BigInteger。
getXString 输出恒为：无前导零、无 "+"、负数带 "-"、零为 "0"，不返回 null。

协议/序列化（若 X 走 JSON 或 RPC）：
- 读请求最多出现一个字段：{"x":123} 走旧路径，{"xStr":"12345678901234567890"} 走新路径；两字段同时出现且数值不一致 → E_CONFLICT，一致则接受；
- 写响应：值在 int 范围时同时输出 x 与 xStr（旧客户端可读）；超出 int 时只输出 xStr、省略 x，旧客户端按既有「字段缺失」逻辑处理，绝不拿到错误值；
- 不改变既有字段类型，不把超范围值塞进 x 字段。

兼容与回滚：setX(int) 不校验 MAX_DIGITS（int 天然很小），异常类型、错误码、日志格式不变。新接口以新增方法/新增可选字段落地，服务端先上线读兼容；调用方按需切换 setXString；回滚仅需调用方改回 setX，无需数据迁移（值在 int 范围内可无损降级，超出范围时 setX 无法表达，由业务侧按 E_RANGE 处理）。

测试要点（必须覆盖）：
- int 路径回归：Integer.MIN_VALUE / MAX_VALUE / 0 / -1；
- 数值边界：2^31-1、2^31、2^53、2^63、10^4096-1、10^4096；
- 格式：null、空串、单独符号、前导零、空白、全角数字 → 对应 E_FORMAT；
- 并发：setXString 与 getX/getXString 并发，读到的必须是完整旧值或完整新值（volatile 不可变对象保证）；
- 协议：双字段冲突 → E_CONFLICT；超 int 时旧客户端收到缺失 x 而非错误值。

表态：base 接受 mw 的兼容路线，正式撤回 v1 的「int 改 string」替换方案，v2 唯一采用「保留 int + 新增 setXString/getXString」。理由：在无协议版本协商的前提下，破坏性替换的迁移面与线上风险不可控；具名新增接口可同时满足大整数诉求与零破坏，并为后续再评估「是否废弃 int」保留空间（该议题不在本提案范围，需单独立项）。

关键观察

  • 并行盲投有效：room 第 1 轮 base/mw/app 独立给出不同立场（base 提重载、mw 提可选字段、app 接受原案），未互相锚定。
  • chair 只引导不给方案：chair 判定 continue 并归纳分歧点，由发起方 base 整合出 v2 兼容方案。
  • 确定性兜底生效：状态机强制"未全员接受不得判 agree"，杜绝模型假宣布共识（smoke 测试 5 实测拦截）。
  • 决议 → issue：room 达成后自动为每个参与方生成"决议来源" issue，与普通 issue 区分。
  • 只可追加：所有状态迁移走事件日志，非法迁移（closed 再评审、重复表态）被拒绝。
  • 守则按角色分工生效：修订方 mw 只提「问题 + 诉求 + 一句方向」，发起方 base 负责展开完整方案（API 签名/内部状态/边界/伪代码/测试集齐全），不再越俎代庖。
